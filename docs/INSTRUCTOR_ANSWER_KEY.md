# Ключ решений для преподавателя

> **Содержит готовые ответы. Не передавайте студентам.** Для самостоятельной работы используйте встроенный `/handbook`.

Сценарии описывают конкретные условия зачёта симулятора. Они не являются полным описанием соответствующих уязвимостей в реальных системах.

## Как читать ключ

Учебные запросы отправляются из перехватчика. Метод выбирается отдельно, путь вводится без метода, пустые заголовки и тело задаются как `{}`. Не открывайте учебные API-пути непосредственно в адресной строке.

Для составных заданий выполняйте шаги в одной сессии и используйте значения, выданные ответами. Внешний вызов перехватчика может завершиться успешно, хотя виртуальный ответ задания содержит 401, 403, 409 или 500.

## Покупатель с вопросами

### 1. Набор за один рубль — подмена цены

### Запрос в перехватчике

```text
POST /api/store/orders
```

```json
{
  "product_id": "honey-set",
  "quantity": 1,
  "unit_price": 1
}
```

Для контроля обычный заказ показывает цену 4990. В изменённом ответе ожидаются order_id LAB-2048 и charged 1.


- **Старт:** оформить заказ с товаром «Медовое знакомство».
- **Запрос:** `POST /api/store/orders`; `product_id: "honey-set"`, `quantity: 1`, `unit_price: 1`.
- **Зачёт:** заказ с положительным количеством и ценой не больше 1. Ожидаемый результат — `charged: 1`.
- **Разбор:** цену нужно брать из серверного каталога и вычислять сумму на сервере.

### Подробное объяснение

Начните с обычного заказа и попросите студента назвать, откуда сервер должен брать цену. Затем сравните запрос до и после: меняется только присланное значение цены, а товар и количество остаются прежними. Если итог заказа становится равен одному рублю, сервер доверился данным покупателя.

Для разбора подчеркните, что скрытое поле формы, JavaScript-код и интерфейсная цена всё равно находятся под контролем клиента. Корректный вариант — принимать идентификатор товара и количество, получать цену из собственного каталога, проверять доступность и рассчитывать сумму на сервере. В тесте обычная покупка должна проходить, а произвольная цена клиента — не влиять на сумму.

### 2. Магазин должен вам — отрицательное количество

### Запрос в перехватчике

```text
POST /api/cart/items
```

```json
{
  "sku": "honey-500",
  "quantity": -3
}
```

Штатно одна единица стоит 890. После подмены ожидаются quantity -3 и cart_total -2670.


- **Старт:** добавить товар «Липовый» в корзину.
- **Запрос:** `POST /api/cart/items`; `sku: "honey-500"`, `quantity: -3`.
- **Зачёт:** в ответе отрицательное количество и отрицательный `cart_total`.
- **Разбор:** сервер должен принимать только положительное целое количество в заданных пределах.

### Подробное объяснение

Сопоставьте обычное добавление одной единицы товара с тем же запросом, в котором количество заменено на отрицательное число. Отрицательная стоимость показывает, что значение прошло в расчёт без серверной проверки. Кнопка уменьшения количества не является защитой: пользователь может отправить запрос с любым телом.

Обсудите серверный инвариант: количество должно быть целым и попадать в заданный диапазон. Проверка должна выполняться до обновления корзины и вычисления суммы. Убедитесь в обоих направлениях: допустимое количество принимается, а ноль, отрицательное, дробное и слишком большое значения не меняют состояние корзины.

### 3. Разговорчивая доставка — раскрытие ошибок

### Контроль и запрос

Обычный вариант: GET /api/store/shipments?format=json. Измените тип параметра:

```text
GET /api/store/shipments?format[]=json
```

Учебный ответ 500 содержит TypeError, shipping-worker.internal и трассировку ShipmentController.php:74, Kernel.php:211.


- **Старт:** открыть «Заказы и доставка» и проверить обычную доставку.
- **Запрос:** `GET /api/store/shipments?format[]=json`.
- **Зачёт:** query string содержит `format[]=json`; ожидается учебный 500 с `TypeError`, `shipping-worker.internal` и трассировкой.
- **Разбор:** валидировать тип входа и возвращать безопасную ошибку без внутренних имён и файлов.

### Подробное объяснение

Покажите штатный запрос с одиночным параметром и ответ со списком доставок. Затем измените только форму параметра на массив. Ошибка показывает две разные проблемы: сервер не проверил ожидаемый тип входа, а ответ клиенту раскрыл название внутреннего сервиса и строки трассировки.

Спросите, помогает ли атакующему путь файла или имя компонента продолжить исследование. Обсудите проверку типа на границе API и единый безопасный формат ошибки для клиента. Технические подробности можно сохранить в серверном журнале с ограниченным доступом. Повторная проверка: корректный формат работает, неверный получает контролируемый отказ без внутренней диагностики.

## За дверью кабинета

### 4. Кто вы по версии сервера — mass assignment

### Запрос в перехватчике

```text
PATCH /api/store/profile
```

```json
{
  "display_name": "Студент",
  "role": "instructor"
}
```

Ответ 200 показывает сохранённую роль instructor. Для следующей цепочки повторите запрос с ролью admin.


- **Старт:** сохранить профиль.
- **Запрос:** `PATCH /api/store/profile`; добавить к `display_name` поле `role: "instructor"` (или `"admin"`).
- **Зачёт:** роль изменена на одно из этих значений.
- **Разбор:** разрешать только поля профиля; изменение привилегий должно быть отдельным защищённым действием.

### Подробное объяснение

Сравните список полей обычной формы профиля с полями ответа сервера. Добавленное вручную поле role не приходит из интерфейса, но меняет роль в ответе. Это и есть массовое присваивание: сервер без разбора переносит входные поля в объект модели.

Попросите студента отделить поля редактируемого профиля от административных атрибутов. Исправление — явный список разрешённых полей или отдельная модель входных данных; повышение роли должно быть самостоятельной операцией с проверкой полномочий. Тест должен подтвердить, что имя меняется, а поле role игнорируется либо отклоняется.

### 5. Документ не тому адресату — IDOR

### Запросы по порядку

Сначала прочитайте обращение:

```text
GET /api/support/tickets/42
```

Из ответа возьмите order_ref ORD-b7f3 и запросите связанный счёт:

```text
GET /api/store/invoices/ORD-b7f3
```

Ответ содержит счёт INV-882, покупателя Алису Воронову и сумму 27990.


1. `GET /api/support/tickets/42` — в ответе прочитать `order_ref` и материалы следующего этапа.
2. Запросить указанный счёт: `GET /api/store/invoices/ORD-b7f3`.
3. **Зачёт:** чтение обращения предшествует чтению счёта в той же сессии; результат содержит `INV-882` и данные Алисы.
4. **Разбор:** каждый документ требует отдельной проверки прав текущего пользователя.

### Подробное объяснение

Первый запрос к обращению выдаёт ссылку на связанный счёт. Следующий запрос использует этот идентификатор и получает данные другого покупателя. Разберите, что знание ссылки и факт нахождения идентификатора в доступном обращении не дают права читать сам счёт.

Ключевой вопрос — проверяется ли владелец объекта при каждом обращении. Исправление должно связывать счёт с текущим пользователем или его ролью на сервере. Нельзя полагаться на сложность идентификатора, скрытую ссылку или предыдущий экран. Для проверки сравните доступ к собственному и чужому счёту, включая прямой запрос известного чужого идентификатора.

### 6. Служебный вход — доступ по скрытому адресу

### Запросы по порядку

Прочитайте публичный файл:

```text
GET /robots.txt
```

Найдите Disallow: /internal/export, затем отправьте:

```text
GET /internal/export
```

Учебный ответ содержит customers с alice@example.test и boris@example.test.


1. `GET /robots.txt` — прочитать путь `/internal/export`.
2. `GET /internal/export` — получить учебный список клиентов.
3. **Зачёт:** оба шага выполнены в одной сессии.
4. **Разбор:** скрытый маршрут или robots.txt не заменяет серверную авторизацию.

### Подробное объяснение

Сначала студент находит путь в robots.txt, затем открывает его напрямую и получает экспорт. robots.txt сообщает поисковым роботам, какие страницы не индексировать; он публичен и не должен защищать данные.

Обсудите разницу между сокрытием маршрута и авторизацией. Даже если убрать пункт меню и запись из robots.txt, сервер обязан проверять разрешение на каждом запросе экспорта. Исправление — требовать аутентификацию и соответствующую роль на сервере. Тест: обычный студент получает отказ при прямом запросе, а уполномоченный пользователь получает только разрешённые данные.

### 7. Следы в журнале — повышение привилегий

### Запросы по порядку

Сначала измените профиль:

```text
PATCH /api/store/profile
```

```json
{
  "display_name": "Студент",
  "role": "admin"
}
```

Затем вызовите журнал:

```text
GET /api/admin/audit
```

Заголовки: {"X-Lab-Role":"admin"}. Тело: {}. Ответ содержит событие export.created.


1. `PATCH /api/store/profile` с `role: "admin"`.
2. `GET /api/admin/audit` с заголовком `X-Lab-Role: admin`.
3. **Зачёт:** история содержит оба действия; ответ журнала содержит событие `export.created`.
4. **Разбор:** сервер не должен принимать полномочия из поля профиля или заголовка клиента.

### Подробное объяснение

Это составная цепочка из предыдущей ошибки профиля и доверия к заголовку. Сначала запрос профиля устанавливает роль admin. Затем отдельный запрос к журналу передаёт эту роль в X-Lab-Role. Условие зачёта требует оба шага, потому что цель — проследить цепочку, а не только увидеть конечный ответ.

Разберите, почему заголовок не доказывает полномочия: клиент может сформировать его самостоятельно. Сервер должен извлекать роль из защищённого состояния сессии и применять проверку доступа к каждой административной операции. Тесты должны отклонять поддельный заголовок и попытку изменить роль через профиль, сохраняя доступ настоящего администратора.

## Когда текст становится кодом

### 8. Поиск с побочным эффектом — отражённый XSS

### Запрос в перехватчике

```text
GET /api/search?q=%3Csvg%20onload%3Dalert(1)%3E
```

Исходная строка: <svg onload=alert(1)>. Ответ содержит HTML-предпросмотр с учебным alert. Поддерживается также шаблон img/onerror с alert(1).


- **Старт:** выполнить поиск в разделе отзывов и поиска.
- **Ввод:** `<svg onload=alert(1)>` (поддерживается также учебный шаблон с `img/onerror`).
- **Зачёт:** распознан учебный обработчик с `alert(1)`; HTML-предпросмотр показывает учебный alert.
- **Разбор:** контекстное кодирование вывода и безопасные текстовые узлы; CSP — дополнительный уровень защиты.

### Подробное объяснение

Сначала обычным поиском найдите место, где введённая строка появляется в ответе. Затем замените её на учебную разметку и сравните вывод. В этом сценарии значение возвращается сразу, не сохраняясь на будущее, поэтому тип ошибки — отражённый XSS.

Объясните разницу между отображением текста и интерпретацией его как HTML. Исправление — безопасный текстовый вывод или контекстное кодирование для того места, где вставляются данные. CSP может уменьшить последствия, но не исправляет небезопасный вывод. Проверка: тестовая строка видна как текст, обработчик не исполняется.

### 9. Отзыв с сюрпризом — сохранённый XSS

### Запросы по порядку

Опубликуйте отзыв:

```text
POST /api/comments
```

```json
{
  "content": "<svg onload=alert(1)>"
}
```

Публикация вернёт 201, но зачёта ещё нет. Затем прочитайте ленту:

```text
GET /api/comments
```

Ответ показывает сохранённый HTML и учебный alert.


1. `POST /api/comments` с `content: "<svg onload=alert(1)>"`.
2. Затем `GET /api/comments` или открыть ленту как следующему посетителю.
3. **Зачёт:** payload сначала сохранён, затем прочитан в той же истории студента; публикации недостаточно.
4. **Разбор:** выводить пользовательский текст как текст либо строго санитизировать разрешённую разметку. Изоляция не распространяет отзыв на других студентов.

### Подробное объяснение

У задания два обязательных момента: публикация строки и её последующее чтение. Ответ об успешной публикации сам по себе ещё не подтверждает проблему. После повторного чтения ленты учебный предпросмотр показывает сохранённую строку как исполняемую разметку.

Такой сценарий отличается от отражённого XSS тем, что данные переживают запрос и опасный вывод происходит позже. Исправление — показывать содержимое отзыва как текст либо очищать его строгим списком разрешённых элементов и атрибутов. Проверяйте именно последовательность «сохранить → прочитать снова». В модели записи изолированы между студентами, поэтому это не атака на браузеры одногруппников.

### 10. Товар, которого нет на витрине — SQL-инъекция

### Контроль и запрос

Поиск honey возвращает обычную позицию. Измените фильтр:

```text
GET /api/catalog?filter=%27%20OR%201%3D1--
```

Исходное значение фильтра: ' OR 1=1--. В ответе появится hidden-queen — Маточное молочко, hidden: true.


- **Старт:** поиск каталога через `/api/catalog`.
- **Ввод:** `' OR 1=1--` в параметр `filter`.
- **Зачёт:** появляется `sku: "hidden-queen"` с `hidden: true`.
- **Ограничение модели:** произвольный SQL не выполняется; изменяющие команды блокируются.
- **Разбор:** параметризованные запросы и отдельная серверная проверка видимости.

### Подробное объяснение

Для контроля обычный фильтр honey показывает одну позицию. Затем строка с кавычкой и логическим условием приводит к появлению скрытого товара. Попросите студента объяснить, как ввод мог изменить условие поиска, а не просто стать значением фильтра.

В модели базы данных запрос не исполняется: движок распознаёт учебную конструкцию и возвращает заранее заданный результат. В реальном коде защита строится на параметризованных запросах и отдельной проверке права показывать скрытые товары. Тест: строка с SQL-синтаксисом обрабатывается как обычный ввод и не расширяет результаты.

## Чужая личность

### 11. Кто здесь зарегистрирован — перечисление пользователей

### Запросы для сравнения

Сначала неизвестный пользователь:

```text
POST /api/auth/login
```

```json
{
  "email": "missing@example.test",
  "password": "wrong"
}
```

Затем Алиса с тем же паролем:

```json
{
  "email": "alice@example.test",
  "password": "wrong"
}
```

Оба ответа 401, но code различается: account_missing и password_invalid.


1. `POST /api/auth/login` с `missing@example.test` и неверным паролем: ответ `account_missing`.
2. Повторить с `alice@example.test` и тем же неверным паролем: ответ `password_invalid`.
3. **Зачёт:** обе попытки в указанном порядке в одной сессии.
4. **Разбор:** одинаковый статус недостаточен, если код или текст ответа различаются. Унифицировать отказ, время обработки и ограничивать попытки.

### Подробное объяснение

Две попытки входа используют одинаковый неверный пароль, но разные адреса. Для отсутствующего адреса сервер отвечает account_missing, а для существующего — password_invalid. Разница сообщает, зарегистрирован ли пользователь, даже если оба ответа имеют статус 401.

Обсудите, как унифицировать текст и код ответа, ограничить частоту попыток и не допустить заметного различия по времени обработки. Проверка должна сравнивать не только HTTP-статус, но и тело ответа и наблюдаемое поведение для существующего и отсутствующего аккаунта.

### 12. Письмо, которое вам не присылали — предсказуемый токен

### Запросы по порядку

Запросите собственный токен:

```text

### Подробное объяснение

Начать нужно с собственного адреса: ответ показывает закономерность токена. В данной модели к локальной части email добавляется постоянный суффикс 2609. После этого студент выводит значение для Алисы и отправляет его вместе с её адресом. Сценарий подтверждает токен, но не меняет настоящий пароль.

Исправление — криптографически случайный одноразовый токен с ограниченным сроком и привязкой к конкретной учётной записи. Проверяйте повторное использование, истечение срока и попытку применить токен к другому аккаунту.

```

2. Вызвать `POST /api/auth/session` с этой транзакцией, не отправляя OTP.
3. **Зачёт:** правильные данные первого шага и завершение с выданной транзакцией; ожидается `mfa_verified: false`.
4. **Разбор:** сессию выдавать только после серверной проверки полного процесса MFA. Учебный OTP endpoint всегда возвращает 422.

### Подробное объяснение

Сначала пользователь проходит проверку пароля и получает transaction. Вместо ввода второго фактора он напрямую вызывает endpoint создания сессии с этим значением. Ответ показывает, что сессия создана, хотя mfa_verified остаётся false.

Это демонстрирует, что наличие второго экрана в интерфейсе ещё не означает серверную проверку второго фактора. Состояние процесса должно храниться и проверяться сервером; endpoint завершения обязан отказывать, пока OTP не подтверждён. Успешная проверка должна включать и полный корректный вход, и прямой вызов завершения без второго фактора.

### 14. Один купон, две скидки — гонка состояния
### Контроль и параллельный опыт

Создайте корзину через POST /api/cart/new, тело {}. Возьмите cart_id из ответа. Отправьте одиночный запрос:

```text
POST /api/cart/coupon
```

```json
{
  "code": "HONEY20",
  "cart_id": "cart-1"
}
```

Первый ответ 200; повтор в этой корзине — 409. Создайте новую корзину, используйте её реальный cart_id и отправьте купон в режиме «Параллельно ×2». Ожидаются accepted_requests 2, discounts_applied 2 и comparison_recorded true. Не применяйте купон к новой корзине до опыта.


1. Создать корзину через `POST /api/cart/new`.
2. В режиме «Один запрос» применить `HONEY20` к ней: первый ответ 200, повторный — 409.
3. Создать новую корзину и взять её `cart_id` из ответа.
4. Отправить купон в режиме «Параллельно ×2».
5. **Зачёт:** в новой корзине два принятых запроса и `discounts_applied: 2`; важна последовательность контрольного отказа.
6. **Ограничение модели:** гонка симулируется упорядоченным timeline, не реальными процессами; сумма чека не уменьшается.
7. **Разбор:** атомарная проверка и запись, транзакция/блокировка и уникальность применения.

### Подробное объяснение

Сначала последовательно примените купон дважды к одной корзине: первая операция проходит, вторая должна получить 409. Это контроль нормального ограничения. Затем создайте новую корзину и отправьте один запрос в режиме «Параллельно ×2». Если обе операции читают состояние до того, как одна из них записала использование купона, модель принимает обе.

Объясните временное окно между проверкой и изменением состояния. Реальное исправление должно объединить проверку и запись в атомарную транзакцию, использовать блокировку или уникальное ограничение. Сценарий лишь моделирует порядок событий и не запускает гонку процессов; результатом является timeline и число применений, не снижение суммы чека. Проверка исправления: при конкуренции проходит ровно одно применение.

### 15. По ту сторону сервера — SSRF

### Запросы по порядку

Публичная справка:

```text
POST /api/tools/preview
```

```json
{
  "url": "https://docs.example.test/help"
}
```

Внутренний индекс:

```json
{
  "url": "http://metadata.internal/latest/"
}
```

Найденный в индексе ресурс:

```json
{
  "url": "http://metadata.internal/latest/secret"
}
```

Финальный ответ содержит upstream metadata.internal и LAB-METADATA-KEY=bee-7f91. Все ответы виртуальные, сеть не вызывается.


1. Запросить штатный адрес справки `https://docs.example.test/help` через `POST /api/tools/preview`.
2. Из открывшихся материалов получить и запросить `http://metadata.internal/latest/`.
3. Из индекса получить и запросить `http://metadata.internal/latest/secret`.
4. **Зачёт:** все три запроса в указанном порядке; финальный ответ содержит `LAB-METADATA-KEY=bee-7f91`.
5. **Ограничение модели:** реальных сетевых запросов нет.
6. **Разбор:** ограничить допустимые адреса и проверять назначение после DNS-разрешения и перенаправлений.

### Подробное объяснение

В первом запросе серверный предпросмотр загружает публичную учебную справку. Её ответ раскрывает внутренний индекс, а индекс — следующий адрес с секретом. Студент проходит цепочку из трёх запросов; прямой запрос последнего адреса не засчитывается, потому что не показывает ход исследования.

Обсудите, что сетевой запрос выполняет сервис на сервере, а не браузер пользователя. В реальном приложении это может открыть доступ к внутренним ресурсам. Этот проект только моделирует ответы и не обращается к сети. Защита должна ограничивать назначения, проверять DNS-результат и повторно проверять адрес после перенаправлений. Проверка: разрешённая внешняя справка доступна, внутренние IP и переходы к ним запрещены.

### 16. Подпись директора — подмена JWT

### Запросы по порядку

Получите учебный токен:

```text
GET /api/auth/lab-token
```

Проверьте его на GET /api/admin/reports с заголовком Authorization: Bearer исходный_токен — ожидается 403. Исходное значение:

```text
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJzdHVkZW50Iiwicm9sZSI6InN0dWRlbnQifQ.c2lnbmF0dXJl
```

Затем замените токен на значение с alg none, ролью admin и пустой подписью:

```text
eyJhbGciOiJub25lIn0.eyJzdWIiOiJzdHVkZW50Iiwicm9sZSI6ImFkbWluIn0.
```

Повторите GET /api/admin/reports с Authorization: Bearer новым_токеном и телом {}. Ожидаются статус 200, роль admin и отчёт «Выручка: 1 240 000 ₽». Финальная точка обязательна.


1. `GET /api/auth/lab-token` — получить собственный токен.
2. Запросить `GET /api/admin/reports` с исходным токеном; ожидается 403.
3. Создать учебный токен с заголовком `{"alg":"none"}`, payload `{"sub":"student","role":"admin"}` и пустой третьей частью:

   `eyJhbGciOiJub25lIn0.eyJzdWIiOiJzdHVkZW50Iiwicm9sZSI6ImFkbWluIn0.`

4. Повторить запрос отчёта с новым токеном.
5. **Зачёт:** исходный токен получен; изменённый токен содержит `alg=none`, роль `admin` и пустую подпись. Ответ раскрывает учебный отчёт.
6. **Разбор:** фиксированный allowlist алгоритмов, проверка подписи и обязательных claims. Base64url — кодирование, а не подпись.

### Подробное объяснение

Сначала студент получает собственный токен и проверяет его против административного отчёта: исходная роль даёт 403. Затем меняет заголовок JWT на alg none, payload — на роль admin, а подпись оставляет пустой. Учебный сервис принимает такой токен и возвращает отчёт.

Покажите, что Base64url можно декодировать без секрета: кодирование не подтверждает авторство. Сервер должен фиксировать допустимый алгоритм независимо от заголовка токена, проверять подпись и проверять обязательные claims и права. Проверки: изменённый payload и alg none отвергаются, валидно подписанный токен получает только те права, которые ему выданы.
